## S-1 — Auth rate limit bypassed through `X-Forwarded-For` (Medium)

**Where:** `packages/core/src/client-ip.ts:32`, `apps/web/src/app/actions/auth.ts:40`,
`apps/web/src/app/api/client-errors/route.ts:16`, `docker-compose.yml:19-20`, `SETUP.md:726-749`.

**Evidence:** when neither `CLIENT_IP_HEADER` nor `TRUSTED_PROXY_HOPS` is set and no socket address
is supplied, `getClientIp` sets `trustedHops` to 1 and reads the last `X-Forwarded-For` entry:

```ts
const trustedHops = options.trustedHops || (header || socketAddress !== undefined ? 0 : 1);
```

Next.js does not expose the connection address, so the web app passes no `socketAddress`, and the
client controls the value. The default Compose file publishes port 3000 directly, and the client
documentation's "reached by clients directly — neither setting" row recommends exactly this
configuration. A caller can send its own `X-Forwarded-For` on the server-action POST and obtain a
fresh limiter key for every request, defeating the sign-in, sign-up, and password-reset limits.
The comment in `auth.ts` ("every client shares one count") describes the intended behaviour, not
the implementation.

Start and FastAPI pass the socket address (`apps/start/src/server/client-ip.ts`,
`apps/api-fastapi/src/clubedge_api/rate_limit.py`), so they keep the connection address when
nothing is configured. The Vite server also passes `request.socket.remoteAddress`.

**Impact:** an unauthenticated attacker can attempt credentials without the application's
per-address limit. Provider-side limits still apply, but they are shared by the whole deployment.

**Remediation (branch `fix/security-rate-limit-ip`):** do not infer a trusted hop. Without a
socket address and either setting, use a single `"unknown"` bucket so the limiter fails closed.
Update the documentation and the contradictory comment, and add tests for the no-settings case.

## S-2 — Cloud credentials exposed to same-repository PR code (Medium)

**Where:** `.github/workflows/starter.yml:4,60-69`, `.github/workflows/preview.yml:7,25-34`,
`.github/workflows/stack-previews.yml:5,15-22,42,51-52,74`.

**Evidence:** three workflows run on `pull_request` with long-lived credentials: `APPWRITE_*`,
`NEON_API_KEY`, `SUPABASE_ACCESS_TOKEN`, and `RENDER_API_KEY`. Their guards exclude forks and
Dependabot, but not branches in the same repository:

```yaml
if: >-
  github.event.action != 'closed' && vars.NEON_PROJECT_ID != '' &&
  github.event.pull_request.user.login != 'dependabot[bot]' &&
  github.event.pull_request.head.repo.full_name == github.repository
```

For `pull_request`, GitHub runs the workflow file from the pull request's head. A contributor, bot,
or compromised account with branch-write access can change the workflow in the PR and run arbitrary
code with those credentials. `stack-previews.yml` also grants `contents: write` to that job.

**Impact:** exfiltration of cloud administration keys, database preview data, and repository write
access. Prerequisite: the ability to push a branch to the repository.

**Remediation (branch `fix/security-ci-trust`):** put secret-bearing jobs behind GitHub
Environments that require reviewers, document the required repository settings, and pin the
third-party actions and CLIs used in those jobs.

## S-3 — `safeRedirectPath` can return a protocol-relative URL (Low)

**Where:** `packages/core/src/redirect.ts:13-16`, `apps/web/src/app/auth/callback/route.ts:20-27`,
`apps/start/src/server/auth-forms.ts:166-172`.

**Evidence:** the function rejects values that start with `//`, then normalises through `URL`.
Normalisation can introduce a second leading slash:

```text
new URL("/..//evil.example", "http://localhost")
  -> origin "http://localhost", pathname "//evil.example"
```

The origin check passes, and the callback writes the returned string into `Location` unchanged, so
the browser navigates off-site.

**Reachability:** no victim-side path was demonstrated. The login pages re-run the sanitiser on the
hidden `next` value, which rejects the `//` result, and the callback only redirects after a
successful PKCE exchange that needs the verifier cookie of the browser that started the flow. This
is a latent redirect bug: the sanitiser breaks its own contract, and a future caller that uses it
directly would be exploitable.

**Remediation (branch `fix/security-web-hardening`):** reject a normalised path that starts with
`//`, and add the normalisation cases to `redirect.test.ts`.

## S-4 — Push device removal and rebinding need no authentication (Low)

**Where:** `apps/api/src/routes/push.ts:99-107`, `packages/push/src/devices.ts:22-36`.

**Evidence:** `POST /api/push/devices/remove` has no `signedIn` middleware and deletes a row by
token alone. Registration uses an upsert that reassigns an existing token to the current user.
Anyone who knows a token can stop that device's notifications or move it to another account.

**Impact:** denial of notifications for a known token. The token is a long random value, so this is
a bearer-capability tradeoff rather than a cross-user read. The unauthenticated removal exists so
the app can forget a token after sign-out.

**Remediation (branch `fix/security-push-devices`):** keep the sign-out path, document the token as
a bearer capability, and add a registration rate limit and a per-user device ceiling so a token
cannot be abused at scale.

## S-5 — Push devices and test sends have no per-user ceiling (Low)

**Where:** `apps/api/src/routes/push.ts:75-123`, `packages/push/src/devices.ts:55-71`.

**Evidence:** a signed-in user can register any number of format-valid tokens, and
`POST /api/push/test` fans a notification out to every device, five times a minute. A single account
can consume the push provider's quota (and any per-message cost) with tokens it invents.

**Remediation (branch `fix/security-push-devices`):** cap devices per user, rate-limit
registration, and optionally verify tokens with the provider before keeping them.

## S-6 — Account deletion leaves a live `past_due` subscription orphaned (Low)

**Where:** `apps/api/src/server/account.ts:23-36`, `packages/payments/src/types.ts:67`,
`packages/payments/src/schema.ts:17-19`, `packages/payments/src/billing.ts:86-119`,
`apps/api/src/routes/billing.ts:124-126`.

**Evidence:** deletion is refused only while `isEntitled` is true, which covers `active` and
`trialing`. A `past_due` subscription lets the deletion proceed: the `users` row goes, the
`subscriptions` row follows by cascade, and the provider subscription stays live. A later
`customer.subscription.*` event carries `metadata.userId`, tries to insert a row for the deleted
user, violates the foreign key, and returns 500. The event insert is in the same transaction, so the
event is not recorded and the provider keeps retrying. The code comment says the subscription is
"cancelled first"; nothing cancels it.

**Impact:** billing continues for an account that no longer exists, and the webhook delivery keeps
failing. This is an integrity and billing issue, not an authorization bypass.

**Remediation (branch `fix/security-billing-lifecycle`):** refuse deletion while any provider
subscription is live, and make webhook application tolerate a deleted user (record the event and
ignore it instead of returning 500).

## S-7 — Self-hosted Vite server omits security headers (Low)

**Where:** `apps/vite/server.mjs:213-219`, `apps/web/next.config.ts:23-29`,
`apps/start/src/start.ts:8-14`.

**Evidence:** the Vite server sends only `content-length`, `content-type`, and `cache-control`.
Next and Start send `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`,
`Permissions-Policy`, and `Strict-Transport-Security`. The Vite stack is therefore frameable and
lacks HSTS when self-hosted.

**Remediation (branch `fix/security-web-hardening`):** send the same five headers from the Vite
server, including on the API proxy responses where applicable.

## S-8 — Mutable CI actions and CLIs run with production credentials (Low)

**Where:** `.github/workflows/deploy.yml:16,29,59-61,78`,
`.github/workflows/expo-release.yml:65`, `.github/workflows/expo-update.yml:55`,
`.github/workflows/clubedge-upgrade.yml` (upgrade step), `.github/workflows/starter.yml:50`.

**Evidence:** `setup-flyctl@master` and several `@latest` CLIs run with `FLY_API_TOKEN`,
`VERCEL_TOKEN`, `NETLIFY_AUTH_TOKEN`, `RAILWAY_TOKEN`, and `EXPO_TOKEN`; the upgrade workflow runs
`@clubedge/create-clubedge-app@latest` with `contents`, `pull-requests`, and `actions: write`. The
actionlint installer is piped from `curl` at a mutable tag. A compromised package, tag, or action
runs with the deployment identity.

**Remediation (branch `fix/security-ci-trust`):** pin actions by commit SHA and CLIs by exact
version (or keep them in `devDependencies` with the lockfile), and verify downloaded release
artefacts.

## Verified clean

- CSRF: Next server-action origin checks, Start's `createCsrfMiddleware`, and the API's `jsonOnly`.
- CORS: an explicit origin allowlist without credentials.
- Payments webhooks: signature over the raw body, transactional event deduplication, 400/500 split.
- Storage: path containment and symlink handling in the local adapter; provider policies untouched.
- SSRF: the Vite proxy uses a fixed endpoint allowlist and a fixed `API_URL` origin, and strips
  caller-supplied address headers.
- XSS: no `dangerouslySetInnerHTML`, `eval`, or `postMessage` sinks; React escaping throughout.
- SQL: Drizzle parameterised queries; no user input concatenated into SQL.
- Secrets: `.env` files excluded from the Docker build context; only publishable keys reach clients;
  fork pull requests receive no secrets.
- Containers: non-root runtime users.
- Authentication: bearer tokens are verified with the provider (`getUser` / `getSession`), and
  Appwrite and Firebase cookies are `httpOnly` and `sameSite=lax`.
